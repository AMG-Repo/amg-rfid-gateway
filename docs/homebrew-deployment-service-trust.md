# Homebrew system-service trust contract (SERVICE-TRUST-1)

**Decision:** A future Homebrew gateway service must use an explicitly controlled systemd **system** unit with a dedicated non-root account. A Homebrew-generated unit alone is not acceptable. This is a proposed evidence and refusal contract, not an installed unit, device observation, or authorization to prepare files, install a unit, start, enable, or activate anything. The legacy `/opt` unit is outside this contract.

## Source facts, not device evidence

- The [pinned public tap formula at commit `806fd907dd029117e83728c28891e8ed86e6cacb`](https://raw.githubusercontent.com/AMG-Repo/homebrew-tap/806fd907dd029117e83728c28891e8ed86e6cacb/Formula/amg-rfid-gateway.rb) declares a service running `opt_bin/"gateway"`, with `working_dir` under `var/lib/amg-rfid-gateway`, `keep_alive`, and logs. It does not explicitly specify a user or Linux unit name. This does not establish the installed formula revision or the unit on a device.
- The [Homebrew manpage](https://docs.brew.sh/Manpage) describes `sudo brew services` as system scope, installed under `/usr/lib/systemd/system` and started at boot; without sudo, services run in user scope. The [upstream service-generator snapshot at commit `13b273ac7ebcd64fb1a1c7a014d1ba557874b447`](https://raw.githubusercontent.com/Homebrew/brew/13b273ac7ebcd64fb1a1c7a014d1ba557874b447/Library/Homebrew/service.rb) does not emit `User=` in its systemd unit. This pinned upstream snapshot is **not** evidence of the installed Brew version or its generated bytes.
- [systemd.exec(5)](https://man7.org/linux/man-pages/man5/systemd.exec.5.html) specifies that a system manager service without `User=` defaults to root. Thus assuming a generated system unit has non-root execution is unsafe; neither these public sources nor a fixture proves the actual device unit or process identity.

## Required trust boundary before a future transition

An independently acquired, short-lived observation must bind **one exact system manager instance and boot identity** to **one exact unit name**. It must identify the unit load state, active/substate, enablement and masking state, and the root-controlled fragment plus every effective drop-in, including their origin, content identity and precedence. Resolve effective directives, not just a displayed fragment: prove explicit `User=` and `Group=` select a provisioned, dedicated non-root account with verified numeric UID/GID and controlled group membership. Bind the effective `ExecStart`, executable bytes, arguments, environment/config inputs, working directory and Homebrew prefix to a separately authenticated installed receipt and selected content identity. Public formula or release byte equality alone does not authenticate that receipt.

The unit and all effective overrides must be controlled by trusted privileged owners without writable ancestors or modification paths available to the service account or other untrusted writers. Confirm the selected data and runtime directory ownership, write access, creation and cleanup across boot/restart/crash, and socket candidate lifecycle without inferring safety from path equality or metadata alone. Before any later start/enable proposal, independently establish required listener confinement and network isolation; zero enabled antennas, an unoccupied socket name, and a modeled service boundary do not prove these properties. Account provisioning, UID/GID, unit filename, exact path bytes, installed formula commit, current state, socket safety, readiness and isolation remain **device unknowns**.

Evidence acquisition must authenticate its origin and bind manager, boot, unit, effective files, account, prefix, receipt, command and selected paths in one bounded record; redact secrets and avoid treating raw caller flags, fixture output or historical tracker text as proof. Re-read and compare the authoritative objects and manager state immediately before each separately authorized future action. A changed boot, manager, unit, directive, file identity, account, executable, receipt, path or state expires the observation. If any component is missing, masked, failed, active, ambiguous, stale or mismatched, refuse the proposed transition without guessing. A stopped observation is necessary but not sufficient for authority.

## Separate gates

| Gate | Contract |
| --- | --- |
| File preparation | May be modeled independently; it installs no unit and grants no service operation. |
| Unit installation | Separate privileged, operator-authorized transaction only after exact evidence, ownership, inverse and interruption recovery are specified and verified. No generated-unit fallback. |
| Start | Separate operator decision after fresh re-read, isolation and readiness preconditions; never an effect of preparation or installation. |
| Enable | Separate operator decision after fresh re-read; boot persistence is not implied by start. |
| Activation | Requires its own runtime and network evidence; neither a snapshot nor a fixture grants it. |

The current `ServiceBoundary` models only file preparation as potentially proposed; unit transition, start, enable and activation remain false. `service_state_unverified` remains a blocker and `ApplyEligible=false`. DEVICE-GATE remains NO-GO. This document provides no service-manager adapter, live proof, apply caller or permission to act on the Raspberry.

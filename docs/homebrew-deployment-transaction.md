# Local data-directory transaction (fixture-only)

## Separate modeled ownership fixture

`ownershipFixtureTransaction` is a separate package-private exercise with no production caller. Its adapter implementation exists only in `ownership_transaction_test.go`: it stores simulated UID/GID/mode in a test-local map, never calls kernel `chown`, and does not change the fixture's actual owner or mode. It accepts exactly a root directory, one regular file (one link), and one empty directory, with explicit relative paths, kinds, device/inode identities and before/after numeric UID, GID and mode. A complete filesystem walk rejects additional, missing, symlinked or unsupported entries. Its private test journal records the entire inventory, direction, pending/done phase and each object's durable progress; each write syncs a new file, renames it and syncs the parent before progressing. Recovery of a pending record recognizes only recorded before/after modeled states on the same inventoried objects; completed apply is required before a separately selected inverse. A changed inventory, plan, record or unknown state refuses the operation. Incomplete or leftover temporary journal evidence remains untouched and requires diagnosis rather than guessed recovery.

This tests modeled bookkeeping across injected interruptions, **not** kernel ownership, crash durability on a device, hard-link aliases outside the fixture, hostile/concurrent writers, ACLs, mounts, verified content identity, protected journal authority, account provisioning or actual service access. The model has no production apply route, and neither this exercise nor a successful test changes DEVICE-GATE NO-GO or `ApplyEligible=false`. The older mode-only engine below remains unchanged.

`dataTransaction` is package-private and has no production caller, CLI route, apply authorization, service operation, or device integration. Its caller selects one existing owner-owned directory with its device/inode, owner and exact ordinary `0775` precondition, plus a protected journal/lock directory. The current tests use a trusted repository-workspace fixture root, not `/tmp`; fixture cleanup is registered with the test. The engine refuses unsafe ancestors, symbolic links, unexpected owner/group, special bits and object replacement. A cooperative exclusive lock remains tied to the open lock inode; journal entries contain only version, identity, owner, direction and phase, never path or config content.

Ordering: acquire the stable lock and sync its directory; verify the target; write and sync a bounded pending journal file, atomically replace its journal entry and sync the journal directory; reopen the target through its verified parent, check its handle identity and exact mode, change permissions, sync target metadata and parent directory; write and sync durable completion. An explicitly selected rollback reverses `0700 → 0775` only after a durable, matching completed apply on the exact original inode in `0700`; a fresh journal or pending apply cannot authorize it. Pending recovery accepts only the exact before or after mode on that same identity; completion and retries are idempotent. An interrupted `record.new` matching an already durable record is removed and the root synced; without a record, only a valid pending apply on the original `0775` inode may be promoted and synced before mutation. A divergent valid pending apply beside a completed apply may be discarded only while the exact target remains `0700` and apply was selected. A divergent valid pending rollback beside a completed apply may be promoted only while the exact target remains `0700` and rollback was explicitly selected. A recognized completion temp beside its matching pending record may be synced and promoted only when the selected direction, exact identity, and post-mode agree; an interrupted pending apply after completed rollback is likewise recognizable only at the original pre-mode. Every temp promoted to authority is opened and synced first, including retries after an injected sync failure; failure leaves the journal and target unchanged. Sync injection is scoped to each fixture transaction rather than package-global state. Unknown or inconsistent temporary evidence remains untouched and refuses recovery. Ambiguous states, corrupt journals and unsupported directory sync fail closed. Hook failures at step boundaries exercise interruption paths on a real local filesystem. Fixture tests also exercise rollback sync failures, lock contention, exact `0600` journal-file modes including refusal of setuid, setgid, and sticky bits on lock and records, and interrupted cross-direction temporary records. The lock name and open inode are compared during acquisition, but no test demonstrates a hostile replacement in that window; a renamed-away lock inode after acquisition is not detected as hostile same-UID replacement. Filesystem-mode permission tests are not a substitute for actual access-denied syscalls when the running UID can bypass the mode; the instance-scoped sync callback injects a journal `EACCES` in that case. Journal writes and renames use instance-scoped callbacks defaulting to the actual syscalls. Direct write errors, short writes, and rename failures are exercised for pending and completion in both selected directions. A failed write leaves an empty or truncated `record.new`; retry refuses it and preserves that evidence, even when the target is already at the exact post-mode. A failed pending rename leaves recognizable temporary evidence: apply can promote it only on the original pre-mode; rollback can promote it only beside a completed apply on the exact post-apply mode. A failed completion rename leaves a recognizable done entry beside matching pending evidence and the exact post-mode; it can be synced and promoted on retry. No retry claims recovery from incomplete bytes or an unrecognized state. A rollback pending write is unreachable until a durable completed apply exists; completion writes require a durable pending record and the selected transition's exact post-state. These injected syscall errors are not evidence of real kernel `EACCES` under a privileged UID.

This does **not** prove durability on a real device, or defend against hostile same-UID writers replacing paths, the journal, or lock concurrently. It does not authenticate a plan, establish Homebrew provenance, operate on config/runtime/unit surfaces, or authorize application or activation. A later production integration requires an independently reviewed trust and invocation boundary.

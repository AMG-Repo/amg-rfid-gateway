# Conditional Homebrew change proposals (PLAN-3)

`PlanChange` consumes an in-process content observation and explicit selected config, data, runtime, and unit path/metadata snapshots. An observation assembled from caller JSON cannot carry the package-private observation seal; changing any exported observation field after sealing invalidates its digest. The seal only guards in-process value integrity, not filesystem continuity or external provenance. The planner validates selected filesystem metadata, then invokes a bounded config-byte comparison through an actual no-follow reader. That reader checks ancestors (including refusal of unsafe `/tmp`), selected identity/owner/mode, bounded bytes and unchanged handle metadata against the sealed observation digest. The policy requires explicit string `data_path` and `socket_path` keys without duplicate YAML mapping keys at any nesting level and compares them only to the selected data directory and fixed candidate `/run/amg-rfid-gateway/gateway.sock`. Aliases, merge keys, non-string mapping keys, unsupported tags, and excessive YAML depth or node count are refused rather than interpreted. It returns fixed sanitized codes and equality booleans, never raw scalars or parser errors. Byte equality is not a runtime-safety proof: socket parents, ownership, lifecycle and isolation remain unverified. It proposes only the owner-writable `0775 → 0700` change for an existing selected data directory owned by the current user, or no change for `0700`, when its identity, owner, and mode still match. The exact `0775` pre-state is accepted only at that selected data directory without setuid, setgid, or sticky bits, never at ancestors or other surfaces; a historical record alone is not evidence of current metadata. No default targets, creation, deletion, service operations, or mutation are available.

A proposal contains a before condition, expected after condition, and conditional inverse for the *same original directory identity*. These are descriptions, not proofs that an operation or rollback can execute safely. A future apply must separately establish anchored object continuity, durable crash recovery, privilege boundaries, and explicit operator authority. Missing, unsafe, or stale objects produce a refusal without transitions. Blockers include config runtime safety, receipt authenticity, crash recovery, service state, network isolation, future identity continuity, and inverse execution. Tests exercise local safe fixtures and refusal paths, not actual device state, hostile concurrent writers, runtime socket safety or Homebrew provenance.

SERVICE-1 adds a data-only `ServiceBoundary` to the conditional proposal. It marks the existing data-mode transition as file preparation when proposed, while unit transition, start, enable, and activation eligibility remain false. A refusal has no proposed actions. This model does not execute file preparation, install a unit, inspect a service manager, or prove that a real service is isolated or stopped. Fixture tests cover the distinction in the proposal only; they cannot establish freshness, listener confinement, or real service state. `service_state_unverified` remains a blocker.

The CLI `plan` command remains an `unsupported_action` refusal: CLI arguments cannot supply independently verifiable observation provenance or fresh service-manager evidence. No public service-state flag, historical tracker, or synthetic test fixture can authorize a unit transition. Production unit transitions remain impossible until a separately authorized fresh evidence adapter can verify the exact unit and scope. `ApplyEligible` remains false even for a conditional metadata proposal. None of this verifies Raspberry state or permits activation.

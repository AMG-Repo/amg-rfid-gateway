# Static account access contract (ACCOUNT-ACCESS-1)

**Decision:** A future Homebrew systemd **system** service uses a statically provisioned, dedicated non-root identity, not `DynamicUser`. This is a local, non-authorizing policy proposal, not evidence of account provisioning, installed permissions or a device transition. The exact account name, UID, GID and group membership are unresolved. The [service trust contract](homebrew-deployment-service-trust.md) controls effective-unit and activation evidence; DEVICE-GATE remains **NO-GO** and `ApplyEligible=false`.

## Access matrix

Every access assignment below is **future policy**, conditional on verified identities and paths; none describes installed state. “Deployer” means a separately authorized privileged transaction identity, not the service account. Readers are restricted to the minimum named principals, not an implicit shared group. Directory traversal, parent ownership, ACLs and effective access must also be verified; mode bits alone do not prove isolation.

| Surface | Proposed owner; reader / writer | Lifecycle and proof status |
| --- | --- | --- |
| Existing data tree | Dedicated service UID/GID; service reads and writes only required data, deployer has separately authorized privileged recovery access; no other reader or writer. Proposed private directory mode `0700`, with contained objects inventoried and separately constrained. | Preserve existing objects; identity-bound ownership **and** mode migration is future work. Historical Raspberry observation: `pi:pi`, UID/GID 1000, `0775` is **stale**, not a current precondition or desired service identity. Current contents, owner and mode unknown. |
| Config and secret inputs | Trusted privileged owner; service reads only required inputs, never writes; deployer writes only in a separate authorized preparation transaction. No untrusted readers. | Preserve exact secret bytes and constrain parent access. Selected config metadata/bytes can be observed locally, but effective device path, account access and live provenance remain unproved; do not change ownership merely to give service access. |
| Runtime directory and local socket | Dedicated service identity may create/write its own runtime entries; only explicitly selected clients may traverse/connect to the socket, subject to independently verified socket permissions and peer policy. No generic group or world access. | Runtime creation, removal across stop/restart/crash, socket name reuse and client identity are unresolved. The [runtime evidence contract](homebrew-deployment-runtime-evidence.md) observes a candidate, not its creator or lifecycle. Any `RuntimeDirectory=` choice needs effective-unit and device proof; it is not established here. |
| Effective system unit, all overrides, executable and writable ancestors | Trusted privileged owners; service may read only what execution requires and cannot write or replace any of these bytes or parents. Deployer changes them only under separate privileged authority. | Bind effective precedence, content and installed Homebrew receipt to the exact executable and account before a later gate. Public formula and fixture bytes are not installed proof; [service trust](homebrew-deployment-service-trust.md) remains controlling. |
| Service logs | Trusted logging facility/privileged owner, or a separately reviewed destination; service may emit records but must not edit retained records. Readers limited to explicitly authorized operators, not automatically the service. | Actual log destination and access controls are device unknowns. A service log or system journal is **not** the deployment recovery journal; never infer journal read access or filesystem paths from a formula declaration. |
| Deployment recovery journal and lock | Privileged deployer owns a private root and `0600` records/lock; only the authorized transaction identity reads/writes them. Service has no access. | Separate from service logs. The current [fixture transaction](homebrew-deployment-transaction.md) checks invoking UID ownership of records/lock and writes a mode-only data journal; its local layout is not an installed deployment design or proof of a future owner-changing transaction. |

A possible `StateDirectory=` policy must be evaluated separately against the existing data tree: systemd-managed creation or ownership adjustment must **not** silently adopt or migrate it. Upstream [systemd.exec(5)](https://man7.org/linux/man-pages/man5/systemd.exec.5.html) is cited in the existing service-trust document; its `RuntimeDirectory=`/`StateDirectory=` lifecycle behavior is **not independently verified for the installed systemd version or device**. No directive is prescribed as an executable migration step.

## Future ownership migration: object scope and proof

**Scope decision:** Select one existing data-directory root and a bounded, complete inventory of every contained object, including empty directories and regular files. This is a refusal policy for a future collector and transaction, **not** a claim that current code can enumerate, classify, migrate or recover the tree. No recursive ownership operation is authorized by selecting the root alone.

| Candidate object | Future proof or refusal |
| --- | --- |
| Selected root and contained directories | Candidate only when each exact path-to-object binding, directory identity (device/inode), owner, group and mode is freshly recorded; prove complete bounded traversal, trusted ancestry and controlled mutation parents. |
| Contained regular files | Candidate only with the same per-object proof plus necessary content identity and link-count/control evidence; prove no external hard-link alias or untrusted writer can change bytes or metadata. Preserve content, not just mode bits. |
| Mixed UID/GID, ACL-bearing or ambiguous ACL object | Refuse the entire selection unless a separately reviewed policy and collector prove exact existing and intended access; never silently normalize mixed ownership or widen permissions. |
| Symlink, hard-link alias, special object or nested mount | Refuse the entire selection: traversal, aliasing, special semantics and mount-boundary ownership cannot be inferred from root metadata. |
| Unknown/unbounded inventory, substitution race or untrusted same-UID writer | Refuse: matching UID or a repeated pathname is not exclusive control or stable identity. Any unproved ancestry, mount identity, membership or object replacement invalidates the snapshot. |

**Evidence boundary:** A future protected durable record must bind the selected root **and every contained object** to an authenticated, fresh before-state: path relative to the selected root, object kind, device/inode, owner UID/group GID, full relevant mode and ACL status; record regular-file content identity and link/control evidence where needed, plus ancestor identity/access, mount boundaries and trusted-writer exclusion. It must also bind the provisioned target numeric identity, intended exact per-object after-state, installed receipt and effective-unit/account evidence. Unknown target IDs or historical `pi:pi` observations cannot fill these fields. Before any mutation, establish a bounded complete inventory and durable per-object intent; afterwards record and revalidate each exact identity, owner/group/mode and required content/control evidence with durable per-object progress and completion. A path-only record or root-only journal cannot prove a tree transition.

**Interruption and inverse:** A pending or partly completed inventory is not a completed forward transition. If even one object's identity, before/after state or progress is ambiguous, preserve the evidence and refuse automatic continuation or inversion; do not guess which objects changed or broaden access. An inverse is eligible only after an exact durable completed forward record and fresh proof that **every** selected object remains the recorded expected post-state, including identity, owner/group/mode and necessary content, ancestry and mount control. It restores only the recorded before-state on those same objects, subject to separately reviewed mechanics and authority; any substitution, external modification or missing proof fails closed.

Sprint 2 may only propose a design; Sprint 3 exercises only a separate modeled local fixture with an injected test-only UID/GID/mode adapter and a three-object inventory (root, file, empty directory). Its durable test journal and conditional inverse exercise bookkeeping, not real kernel ownership, installed account access, concurrent-writer exclusion or device durability; see [fixture transaction](homebrew-deployment-transaction.md). Live device observation, privileged mutation and activation each require separate authorization. This policy is not proof of installation or current device state; DEVICE-GATE remains **NO-GO** and `ApplyEligible=false`.

## Future identity-bound migration and recovery contract

1. **Preflight and refusal:** Independently authenticate the installed receipt, exact manager/boot/unit and effective directives, provisioned numeric service UID/GID and memberships, selected config/data/runtime paths, executable, ancestry and contained data ownership/access. Bind fresh device/inode, owner, group, mode and object inventory to protected durable recovery evidence. Prove a stopped, non-activating service boundary and exclusive control of mutation parents; untrusted same-UID writers or ambiguous ACLs fail closed. Refuse if any identity, owner, receipt, unit, runtime, journal/lock or rollback evidence is missing, stale, replaced, inconsistent or inaccessible. No inferred account name or GID.
2. **Proposed order, not executable instructions:** Only after a separate design, tests and operator authorization, establish a trusted private lock and durable pending evidence of the exact before-state, intended service identity and allowable after-state **before** any mutation. An identity-bound future transaction would transfer required ownership of the existing data tree and its necessary contents, constrain access without an intermediate untrusted-readable/writable window, verify the service can access the final tree, then durably record the exact completed state. Apply the object-scope refusal policy above; never bulk-transfer unknown objects. Do not start or enable the service as part of this sequence.
3. **Conditional inverse and interruption:** An inverse is subject to the complete-tree proof above; no inverse on an unknown replacement or merely pending record. At each interruption boundary, recovery must validate durable pending/completion evidence against exact before/after object identities and service/account state; resume or invert only a uniquely proved, separately selected direction, otherwise retain evidence and refuse for human diagnosis. Never guess from a path, widen permissions to restore access, discard ambiguous journal bytes or activate a service during recovery.

The current [change plan](homebrew-deployment-change-plan.md) proposes only `0775 → 0700` while **preserving owner** for a selected directory owned by the invoking UID. The package-private [fixture engine](homebrew-deployment-transaction.md) also preserves owner, requires the invoking UID/GID and supports only that mode transition and its conditional inverse. If the service UID differs from the deployer/legacy owner, `0700` alone **strands the service**. Neither production-facing component implements the ownership migration, its group/contents handling, inverse or crash recovery described above. The separate package-private Sprint 3 fixture does not supply production authority or satisfy the future device proof contract. Config, runtime, receipt, service and recovery blockers remain; `ApplyEligible=false`. A future implementation and independent device gate require separate review and authorization; this contract grants no apply, rollback, unit installation, start, enable or activation authority.

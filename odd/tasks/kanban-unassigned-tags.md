# Kanban catalog + unassigned tags (gateway side)

Step 1 of the kanban pilot: the gateway caches the kanban catalog maintained on the VPS, detects tags that are not assigned to any kanban, and lets the operator assign them from the local panel while online. The cloud side (AMG-RFID-Tools-Demo) owns the catalog and the assignment endpoint; contract coordinated with that session.

## Specs

- S1. Kanban data is maintained on the VPS: "la idea es que desde el vps se actualice la info de los kanban". The gateway only caches it (read-only copy); it never edits kanban data.
- S2. Assigning a tag registers it and requires the VPS online: "en cuanto estado offline asignar conlleva a dar de alta lo ideal seria que se diera de alta desde el vps asi que dejemos el modo offline para asignacion fuera es decir para dar de alta una tag nueva debemos estar online". No offline assignment queue. When the VPS is unreachable the assignment fails visibly and nothing is stored locally.
- S3. Reuse the existing cloud model: "dale reutilicmos la tabla existente" — cloud `kanbans` + `tool_tags.kanban_id` (extended columns), no new entity.
- S4. Unassigned tags: "despues la fixture de tag sin asignar". A read whose EPC is not linked to a kanban appears in an "unassigned tags" list (EPC, antenna, last seen, read count); the operator picks a kanban from the cached catalog and assigns it (S2). The chosen pilot panel (design/local-panel/09-lanes-nox-themes.html) shows them in "Requieren tu atención" with the copy "No se puede registrar un movimiento hasta asignarlo".
- S5. Kanban identity on reads: the operator does not recognize EPCs (L2); reads of assigned tags carry the kanban fields the cloud provides (code, description, standard pack + unit, zone(s), extrusora, positions, customer) so the panel can show the kanban as primary identity.
